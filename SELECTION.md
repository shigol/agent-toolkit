# Selecting shared skills

Use this policy in Claude and Codex. The user's task and project rules govern the work. Skills provide instructions; they do not grant permissions or install task runtimes.

1. Identify the action, deliverable, platform and phase. Codex starts with native skill descriptions and reads the matching source files on demand. When native discovery is absent or coverage is incomplete, follow the project's relevant routes. Hosted Claude project threads use the routes because they do not discover repo skills natively in the tested host. Include local project procedures. Use each workflow that fits a distinct part of the task; choose one primary design workflow. Impeccable is the UI default. Taste requires an explicitly requested alternative direction. Trivial tasks with no matching skill need no forced specialist. An add/update request follows INTAKE.md.
2. When native selection and routes leave a needed capability uncovered, read `.agent-toolkit/catalog/README.md` and choose by meaning. Native discovery and generated routes show the project's selected skills; the full index also covers unlinked groups and skills beyond an optional native_limit. Check coverage of the whole task, not just whether one skill was selected. Honor the project's explicit exclusions and all invocation restrictions even when reading the index. No need to ask the user which skill to use.
3. Search only if the index leaves the fit unclear, or the catalogue is too large to inspect in full. From the project root run:

   `python3 .agent-toolkit/scripts/skills.py search --project . --query "<action, deliverable and platform>"`

   Search reaches the full registered library while respecting explicit exclusions. Read the relevant candidate guides and compare scope, prerequisites and overlaps. A result is a candidate, not proof of readiness. Rephrase once if needed; no match is valid. Do not repeat discovery on every message or load unrelated skill bodies.
4. Read each selected source SKILL.md in full before applying it, plus its required references. For humanizer, read the whole source for documents and outside messages; short replies and PR bodies may use all numbered pattern sections, including their bodies through the last pattern. Headings alone do not establish a read. Humanizer edits free prose, never quotes, data, evidence or required template fields. A previously read, unchanged source can be reused within the same task. Hosted Claude may not expose repo skills through the Skill tool: read the file directly. Use a native `.agents/skills/<name>/SKILL.md` or `.claude/skills/<name>/SKILL.md` link; if unlinked, open the guide's Source path. Preserve manual-only restrictions: `--include-restricted` enables discovery, never implicit invocation.
5. Check the actual environment before execution. Files being present does not establish browser, CLI, credentials, platform compatibility or permission to publish. Follow project setup for missing prerequisites and report a precise blocker if necessary. Never run upstream refresh commands against the pinned checkout.
6. Apply the workflow and verify the task result. Each commit and PR names the skills actually read and used: `Skills: <names>` or `Skills: none (<why>)`. A declared skill is not proof of use; retain actual source reads and relevant check results. Reassess when the task changes phase or platform.

If .agent-toolkit is absent, run the project's documented skills-only setup once. Report timeout/network failures accurately and continue unrelated work. Never fetch a mutable latest revision. Shared changes belong in shigol/agent-toolkit; local procedures stay in their project. Updates reach checkouts through their reviewed update/setup process; running chats do not refresh themselves.

Project owners can generate the shared block with `python3 .agent-toolkit/scripts/toolkit.py emit-routes --project .`, then commit the result. Keep project-only and account-only procedures outside its `skill-routes` markers. Setup regenerates existing owned blocks; `emit-routes --check` fails without changing files if a block is absent or stale, or a routed source does not resolve to the pinned toolkit.
